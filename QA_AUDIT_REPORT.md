## 3. Detailed Bug Reports

### BUG-001 — Default document metadata (title & description)

- **Title:** Page metadata still uses the create-next-app placeholder values.
- **Description:** `app/layout.tsx` exports `metadata` with `title: "Create Next App"` and `description: "Generated by create next app"`. These placeholders ship to production in the `<head>`, harming SEO, social sharing/link previews, and browser-tab identification.
- **Severity:** Medium
- **Priority:** P1
- **Steps to Reproduce:**
  1. Build and serve the app (`npm run build` then `npm run start`).
  2. Load `http://localhost:3000/`.
  3. Observe the browser tab title and view the page source `<head>` (`<title>` and `<meta name="description">`).
- **Expected Result:** A meaningful product title and description that describe this application.
- **Actual Result:** Title renders as "Create Next App"; description renders as "Generated by create next app".
- **Suggested Fix:** Replace the placeholder metadata with real values in `app/layout.tsx`:
  ```tsx
  export const metadata: Metadata = {
    title: "Kiro Web Playground",
    description: "A Next.js playground app for experimenting with Kiro.",
  };
  ```
- **Screenshot reference:** Not applicable (metadata is in `<head>`, not visible in the layout screenshots).

### BUG-002 — Body font overrides the configured Geist font

- **Title:** `globals.css` hard-codes Arial, overriding the Geist `--font-sans` configuration.
- **Description:** `app/layout.tsx` loads Geist/Geist Mono via `next/font/google` and exposes them as `--font-geist-sans`/`--font-geist-mono`, and `app/globals.css` maps `--font-sans: var(--font-geist-sans)` inside `@theme inline`. However, the `body` rule in the same file sets `font-family: Arial, Helvetica, sans-serif`, which wins for the page body. The `font-sans` Tailwind utility on inner elements may re-apply Geist, but the baseline body font is Arial — an internal inconsistency between the font that was imported/configured and the font actually applied to the body.
- **Severity:** Low
- **Priority:** P2
- **Steps to Reproduce:**
  1. Load `/` and inspect `document.body` computed style `font-family`.
  2. Observe it resolves to `Arial, Helvetica, sans-serif` rather than the Geist stack.
- **Expected Result:** The body uses the configured Geist font stack (`--font-sans`), consistent with the `next/font` setup.
- **Actual Result:** The body font-family is `Arial, Helvetica, sans-serif`; the imported Geist font is only applied where the `font-sans` utility is used.
- **Suggested Fix:** Align the body with the configured font variable. In `app/globals.css`:
  ```css
  body {
    background: var(--background);
    color: var(--foreground);
    font-family: var(--font-sans), Arial, Helvetica, sans-serif;
  }
  ```
  Keeping Arial/Helvetica only as a fallback preserves resilience while honoring the Geist configuration.
- **Screenshot reference:** `qa-screenshots/desktop-1440x900.png` (body text renders in the fallback font).

### BUG-003 — Inconsistent external-link behavior and `rel` hygiene

- **Title:** In-paragraph text links lack `target`/`rel`, inconsistent with the CTA anchors.
- **Description:** In `app/page.tsx`, the two in-paragraph links (Templates → `vercel.com/templates`, Learning → `nextjs.org/learn`) are external but have no `target` and no `rel`, so they navigate in the same tab. The two CTA anchors (Deploy Now, Documentation) point to equally external URLs but use `target="_blank" rel="noopener noreferrer"`. This is an inconsistent user experience (some external links replace the current tab, others open a new one) and a minor security-hygiene gap if the text links are later switched to `target="_blank"` without `rel="noopener noreferrer"`. Confirmed in `runtime.md` (focus order shows `target=null, rel=null` on Templates/Learning).
- **Severity:** Low
- **Priority:** P2
- **Steps to Reproduce:**
  1. Load `/`.
  2. Click the Templates or Learning link — it navigates in the same tab.
  3. Click Deploy Now or Documentation — it opens in a new tab.
- **Expected Result:** Consistent, intentional handling of external links; any `target="_blank"` link carries `rel="noopener noreferrer"`.
- **Actual Result:** Text links open in the same tab with no `rel`; CTA links open in a new tab with `rel="noopener noreferrer"`.
- **Suggested Fix:** Decide on one treatment for external links. If they should open in a new tab, apply the same safe attributes and responsive Tailwind styling, using semantic anchor markup:
  ```tsx
  <a
    href="https://vercel.com/templates"
    target="_blank"
    rel="noopener noreferrer"
    className="font-medium text-zinc-950 underline-offset-4 hover:underline dark:text-zinc-50"
  >
    Templates
  </a>
  ```
  If same-tab navigation is intended for text links, leave `target` off but document the decision for consistency.
- **Screenshot reference:** Not applicable (behavioral, not visual).

### BUG-004 — Missing security response headers

- **Title:** No security response headers are configured.
- **Description:** `headers.log` confirms that on the document response for `/`, all six commonly recommended security headers are **absent**: `Content-Security-Policy`, `X-Frame-Options`, `Strict-Transport-Security` (HSTS), `X-Content-Type-Options`, `Referrer-Policy`, and `Permissions-Policy`. `next.config.ts` defines no `headers()` entry, so nothing adds them. While this is a static marketing page with no sensitive data, these headers are baseline hardening (clickjacking protection, MIME-sniffing protection, referrer control, transport security) expected before production exposure.
- **Severity:** Medium
- **Priority:** P1
- **Steps to Reproduce:**
  1. Build and serve the app.
  2. Run `curl -I http://localhost:3000/`.
  3. Observe none of the six headers above are present.
- **Expected Result:** Standard security headers present on the document response.
- **Actual Result:** All six headers absent (see `headers.log`).
- **Suggested Fix:** Add a `headers()` function to `next.config.ts` (verify directives against your deployment before enabling, especially CSP):
  ```ts
  const nextConfig: NextConfig = {
    async headers() {
      return [
        {
          source: "/:path*",
          headers: [
            { key: "X-Frame-Options", value: "DENY" },
            { key: "X-Content-Type-Options", value: "nosniff" },
            { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
            { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" },
            { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" },
            { key: "Content-Security-Policy", value: "default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'" },
          ],
        },
      ];
    },
  };
  ```
  Note: HSTS only takes effect over HTTPS; validate the CSP against the self-hosted font/script chunks before enforcing.
- **Screenshot reference:** Not applicable (header-level finding).

### BUG-005 — `X-Powered-By: Next.js` information disclosure

- **Title:** Framework identity leaked via `X-Powered-By` header.
- **Description:** `headers.log` shows `X-Powered-By: Next.js` present on the document response. This discloses the framework to clients and scanners and is conventionally removed in production.
- **Severity:** Low
- **Priority:** P2
- **Steps to Reproduce:**
  1. Run `curl -I http://localhost:3000/`.
  2. Observe `X-Powered-By: Next.js` in the response.
- **Expected Result:** No framework-identifying header in production responses.
- **Actual Result:** `X-Powered-By: Next.js` is present.
- **Suggested Fix:** Disable it in `next.config.ts`:
  ```ts
  const nextConfig: NextConfig = {
    poweredByHeader: false,
  };
  ```
- **Screenshot reference:** Not applicable (header-level finding).

### BUG-006 — Minimal semantic landmark structure

- **Title:** Page exposes only a `<main>` landmark.
- **Description:** `app/page.tsx` wraps content in a single `<main>` inside a `<div>`; there is no `<header>`, `<nav>`, or `<footer>`. For the current minimal content this is acceptable, but as the page grows (navigation, branding, footer links) the lack of semantic landmarks will hurt assistive-technology navigation. The steering guidance (`steering/demo.md`) requires semantic HTML for all layout sections, so this is flagged proactively at low severity.
- **Severity:** Low
- **Priority:** P3
- **Steps to Reproduce:**
  1. Load `/` and inspect the DOM / run a landmark audit.
  2. Observe only one landmark region (`main`).
- **Expected Result:** Layout sections use appropriate semantic landmarks when present.
- **Actual Result:** Only `<main>` exists; the outer container is a non-semantic `<div>`.
- **Suggested Fix:** When layout sections are added, use semantic landmarks with responsive Tailwind utilities, for example:
  ```tsx
  <header className="w-full px-6 py-4 sm:px-16">{/* brand / nav */}</header>
  <main className="flex w-full max-w-3xl flex-1 flex-col px-6 py-16 sm:px-16">{/* content */}</main>
  <footer className="w-full px-6 py-6 text-sm text-zinc-600 sm:px-16 dark:text-zinc-400">{/* links */}</footer>
  ```
- **Screenshot reference:** `qa-screenshots/desktop-1440x900.png` (single centered content region).

## 4. UX Improvement Suggestions

These are improvement opportunities (several overlap with the bugs above) and are actionable without expanding scope:

- **Set meaningful metadata (ties to BUG-001):** a real title and description improve tab identity, SEO, and link previews. Consider adding Open Graph / Twitter card metadata if this page is ever shared.
- **Make external-link behavior consistent (ties to BUG-003):** choose same-tab vs new-tab deliberately for all external links and apply it uniformly; add a subtle `hover:underline` affordance on the in-paragraph links so they read as links beyond color alone.
- **Resolve the font inconsistency (ties to BUG-002):** letting the configured Geist font apply to the body gives a consistent, intentional typographic baseline across the whole page.
- **Introduce semantic landmarks as the page grows (ties to BUG-006):** `<header>`, `<nav>`, and `<footer>` with responsive Tailwind utilities improve both structure and assistive-tech navigation, per `steering/demo.md`.
- **Add a visible "skip to content" link** once navigation exists, so keyboard users can bypass repeated header/nav links.
- **Keep the strong responsive behavior:** the mobile-centered / `sm:`-left-aligned layout and dark-mode support already work well (screenshots confirm) — preserve this pattern in future sections.

## 6. Accessibility Findings

**Passing / positive observations (evidence-backed):**

- **Image alt text present:** both `next/image` elements have descriptive `alt` text ("Next.js logo", "Vercel logomark") — source-confirmed in `app/page.tsx`.
- **Language declared:** `<html lang="en">` is set in `app/layout.tsx`, enabling correct screen-reader pronunciation.
- **Logical keyboard order:** `runtime.md` records a natural source-order tab sequence — Templates → Learning → Deploy Now → Documentation — with no `tabindex` overrides.
- **Visible focus indicators:** all four links show a visible focus ring (`outline-style: auto`, `outline-width: 1px`); nothing suppresses the default outline, and the ring color adapts to light/dark backgrounds.
- **Heading structure:** exactly one `<h1>` ("To get started, edit the page.tsx file.") — appropriate for a single-topic page; no skipped-level issues given the minimal content.

**Issues / opportunities:**

- **Minimal landmarks (BUG-006):** only `<main>` is present; no `<header>`/`<nav>`/`<footer>`. Acceptable for current content, flagged for growth.
- **Color contrast of muted body text:** the paragraph uses `text-zinc-600` on a white/`zinc-50` background (light) and `text-zinc-400` on black (dark). Tailwind `zinc-600` (#52525b) on white yields a contrast ratio of roughly 7:1, and `zinc-400` (#a1a1aa) on `#0a0a0a` yields roughly 7–8:1; both comfortably meet **WCAG 2.1 AA (4.5:1 for normal text)** and the light-mode value also meets **AAA (7:1)**. No contrast failure observed, but any future reduction of these shades should be re-checked against AA.

**Not Applicable:** form-label associations, ARIA for custom widgets, modal focus-trapping, and table header semantics are N/A — none of those components exist.

## 7. Performance Findings

Grounded in `build.log` and `runtime.md`:

- **Build:** production build succeeds in ~4.4s wall time (Compiled ~1509ms, TypeScript ~1390ms, 4 static pages generated in ~275ms), with **no warnings** (`build.log`). Both routes (`/` and `/_not-found`) are **prerendered as static** (`○`), so the page is served as static HTML with no per-request rendering cost.
- **Bundle sizes:** This Next.js 16.2.4 (Turbopack) build output does **not** print per-route First Load JS byte sizes, so no specific KB figures are claimed here.
- **Network footprint:** ~14 requests per load, all **HTTP 200**, all **same-origin** — 1 document, 1 CSS chunk, ~8 JS chunks (incl. Turbopack runtime), 2 self-hosted `next/font` Geist `.woff2` files, `next.svg`, `vercel.svg`, and `favicon.ico` (`runtime.md`). No third-party/CDN runtime dependency, which removes external-latency and privacy risk.
- **Fonts:** Geist is loaded via `next/font` and self-hosted (no external Google Fonts request at runtime), avoiding render-blocking third-party font fetches.
- **Images / layout stability:** the Next.js logo uses `priority` with fixed `width={100} height={20}`, and no layout shift or overflow was observed (`runtime.md`), which avoids image-driven CLS.
- **Caching:** the prerendered document is served with `s-maxage=31536000`; static SVGs with `public, max-age=0`; favicon with `public, max-age=0, must-revalidate` (`headers.log`).

**Assessment:** For a tiny static page the runtime performance is excellent — fast static delivery, no failed/404/500 requests, no console noise, no CLS, and no external dependencies. No performance defects were found.
