### BUG-001 — Critical Remote Code Execution in Next.js 16.2.4 (Windows servers)

**Severity:** Critical  
**Priority:** P0  
**Component:** Dependencies — `next@16.2.4`

**Description:**  
CVE GHSA-p293-qw3h-jr36 — "Unauthenticated Remote Code Execution on Windows-hosted servers" — CVSS 9.0. Affects `next >= 16.0.0 < 16.3.3`. The installed version is 16.2.4.

**Steps to reproduce:**  
1. Deploy the app as-is on a Windows server.
2. Send a crafted path-traversal request to the Next.js server.
3. Unauthenticated RCE is achievable.

**Expected result:** Application is not exploitable via this vector.  
**Actual result:** Application is running a vulnerable version.  
**Suggested fix:** Upgrade `next` to `>= 16.4.4` (or latest stable): `npm install next@latest`.

### BUG-003 — No HTTP Security Headers

**Severity:** High  
**Priority:** P1  
**Component:** `next.config.ts` — Security Headers

**Description:**  
The application ships with no HTTP security headers. The following headers are absent:

| Header | Risk |
|---|---|
| `Content-Security-Policy` | XSS via script injection |
| `X-Frame-Options` | Clickjacking |
| `X-Content-Type-Options` | MIME sniffing |
| `Referrer-Policy` | Data leakage in Referer header |
| `Permissions-Policy` | Browser feature abuse |
| `Strict-Transport-Security` | Downgrade attacks |

**Steps to reproduce:**  
1. Deploy the app and inspect response headers via `curl -I https://<host>/`.  
2. None of the above headers are present.

**Expected result:** Security headers returned on every response.  
**Actual result:** No security headers in responses.  
**Suggested fix:** Add a `headers()` function to `next.config.ts`:
```ts
async headers() {
  return [
    {
      source: '/(.*)',
      headers: [
        { key: 'X-Content-Type-Options', value: 'nosniff' },
        { key: 'X-Frame-Options', value: 'DENY' },
        { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
        { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
        { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
      ],
    },
  ];
}
```

### BUG-004 — No "Skip to Main Content" Link (Accessibility)

**Severity:** Medium  
**Priority:** P2  
**Component:** `app/layout.tsx` — Accessibility

**Description:**  
There is no skip-navigation link at the top of the page. Keyboard-only and screen reader users must tab through all focusable elements on every page load before reaching the main content area. WCAG 2.1 Success Criterion 2.4.1 (Bypass Blocks) requires a mechanism to skip repeated navigation blocks.

**Steps to reproduce:**  
1. Open the page in a browser.  
2. Press Tab — focus starts on the Next.js logo's parent, then moves through the two inline links in the paragraph, then to the two CTA buttons.  
3. There is no shortcut to jump directly to the `<main>` content.

**Expected result:** First Tab stop is a "Skip to main content" link anchoring to `#main-content`.  
**Actual result:** No skip link exists.  
**Suggested fix:**  
In `app/layout.tsx`, add before `{children}`:
```tsx
<a href="#main-content" className="sr-only focus:not-sr-only focus:absolute focus:top-4 focus:left-4 focus:z-50 focus:px-4 focus:py-2 focus:bg-white focus:text-black focus:rounded">
  Skip to main content
</a>
```
Add `id="main-content"` to the `<main>` element in `page.tsx`.

### BUG-005 — Missing Focus Indicator Styles

**Severity:** Medium  
**Priority:** P2  
**Component:** `app/globals.css`, `app/page.tsx` — Accessibility

**Description:**  
No custom focus ring styles are applied to any interactive element (links, buttons). If the browser's default `:focus` outline is overridden (which Tailwind's preflight/reset can suppress), keyboard users cannot tell which element is focused. WCAG 2.1 SC 2.4.7 requires focus to be visible.

**Steps to reproduce:**  
1. Open the page and press Tab to navigate.  
2. Inspect whether a visible focus ring appears on each link/button.  
3. Tailwind v4's preflight may remove default outlines.

**Expected result:** Clear focus ring on all interactive elements.  
**Actual result:** No `focus:` or `focus-visible:` utilities applied in component markup; risk of invisible focus.  
**Suggested fix:** Add `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-blue-600` to all `<a>` elements in `page.tsx`.

**Severity:** Medium

**Expected result:** Consistent behavior; external links open in new tabs with `noopener noreferrer`.  
**Actual result:** "Templates" and "Learning" navigate in the same tab; no `rel` attribute.  
**Suggested fix:** Add `target="_blank" rel="noopener noreferrer"` to both inline links.

### BUG-010 — 517 KB First-Load JavaScript Bundle

**Severity:** High  
**Priority:** P1  
**Component:** Build / Performance

**Description:**  
The first-load JavaScript for the home page is 528,942 bytes (517 KB) uncompressed per the build diagnostics (`route-bundle-stats.json`). For a static landing page with no interactive components, this is excessive. Even with gzip compression (~50–60% reduction), the wire size would be approximately 200–250 KB. Google's Core Web Vitals guidance recommends keeping Total Blocking Time low; a 517 KB initial JS payload significantly delays Time to Interactive.

**Steps to reproduce:**  
1. Open browser DevTools Network tab.  
2. Load the page and filter by JS.  
3. Observe total JS download and parse cost.

**Expected result:** Minimal JS for a static page — ideally under 100 KB uncompressed.  
**Actual result:** 517 KB of JS loaded on a page with no client-side interactivity.  
**Suggested fix:**  
- Ensure `page.tsx` is a pure Server Component (no `"use client"` directive — confirmed, it is).  
- Consider code-splitting and deferring non-critical chunks.  
- Use Next.js bundle analyzer (`@next/bundle-analyzer`) to identify large dependencies.  
- The current bundle primarily contains React 19 runtime, Next.js client hydration code, and Turbopack runtime. Evaluate if full hydration is necessary for this purely static page.

### BUG-013 — Font Fallback Stack Conflict

**Severity:** Low  
**Priority:** P3  
**Component:** `app/globals.css` — Typography

**Description:**  
`globals.css` sets `body { font-family: Arial, Helvetica, sans-serif; }` as a direct CSS rule. `layout.tsx` applies the Geist font via the CSS variable `--font-geist-sans` mapped to `--font-sans` in the `@theme` block. However, the direct `font-family: Arial` rule on `body` has specificity that may conflict. If Geist fails to load (e.g., network failure, strict CSP blocking Google Fonts), the fallback will render as Arial, not "Geist Fallback" (the metric-compatible fallback with correct ascent/descent overrides that was carefully configured in the CSS). This could cause layout shift.

**Suggested fix:** Change the `globals.css` body font-family to reference the CSS variable: `font-family: var(--font-sans, Arial, Helvetica, sans-serif);`

### BUG-014 — Buttons Potentially Full-Width at `sm` Breakpoint

**Severity:** Low  
**Priority:** P3  
**Component:** `app/page.tsx` — Responsive Layout

**Description:**  
The CTA button container switches from `flex-col` to `sm:flex-row` at 640px. The buttons use `w-full` with `md:w-[158px]`. **Expected result:** Buttons are properly sized at all breakpoints.  
**Actual result:** Buttons may overflow or become undesirably narrow between 640px and 768px.  
**Suggested fix:** Add `sm:w-auto` or `sm:w-[158px]` to the button anchor classes.

## 4. UX Improvement Suggestions

1. **Replace placeholder content** with real application content before any user-facing deployment. The developer-instruction heading and scaffold paragraph text must be replaced.

2. **Add a proper page structure** — include a meaningful `<header>` with the application name/logo, a `<main>` for primary content, and a `<footer>` with copyright and legal links. Currently only `<main>` exists with no context framing.

3. **Add loading states** — while this is a static page, if any client components are added in future they should use React Suspense boundary with appropriate loading skeletons rather than empty states.

4. **Add an error boundary** — there is a `_global-error.html` generated but no custom `error.tsx` or `not-found.tsx` in `app/`. The default Next.js 404 page lacks any styling or brand consistency with the rest of the app.

5. **Dark mode refinement** — the outer `<div>` background is `bg-zinc-50 dark:bg-black` while the `<main>` is `bg-white dark:bg-black`. In dark mode both backgrounds are `#000000`, creating no visual separation. In light mode, the zinc-50 border creates a visible band around the white main content area. Consider removing the outer background or making the main fill the full viewport.

6. **Typography scale** — the h1 (`text-3xl`) to body paragraph (`text-lg`) ratio is appropriate, but there is no secondary heading level or visual hierarchy beyond this. Future content should plan a clear type scale.

7. **Button icon accessibility** — the Vercel logomark image inside the "Deploy Now" button adds visual cue but also has an `alt` attribute set to "Vercel logomark" making screen readers announce "Vercel logomark Deploy Now." Consider changing `alt=""` on the decorative icon to avoid redundant speech.

8. **Add analytics / monitoring** — no error monitoring (e.g., Sentry) or performance monitoring (e.g., Vercel Analytics) is configured. Production deployments should have observability from day one.

9. **Consistent link behavior** — all four external links should have a consistent `target="_blank"` and user-facing hint (e.g., external link icon or `aria-label` suffix "opens in new tab") to avoid surprising users.

10. **Vertical spacing at small viewports** — `py-32` (128px) vertical padding on `<main>` should be reduced at mobile sizes with `py-16 sm:py-24 lg:py-32` to use viewport real estate efficiently.

## 5. Security Findings

### SEC-001 — CRITICAL: Multiple RCEs in Next.js 16.2.4

**Risk level:** Critical  
**CVSS scores:** 9.0, unscored (critical)

Next.js 16.2.4 contains multiple documented Remote Code Execution vulnerabilities. See BUG-001 through BUG-003 for full details. Fix: `npm install next@latest`.

### SEC-002 — HIGH: SSRF via WebSocket Upgrades (CVSS 8.6)

**Advisory:** GHSA-c4j6-fc7j-m34r  
**Risk level:** High  
Next.js applications using WebSocket upgrades are vulnerable to Server-Side Request Forgery. The current app does not use WebSockets explicitly but any future addition creates immediate risk until patched.

### SEC-003 — HIGH: Middleware / Proxy Bypass via Dynamic Route Injection (CVSS 8.1)

**Advisory:** GHSA-492v-c6pp-mqqv  
**Risk level:** High  
Authentication middleware can be bypassed through crafted route parameters. While this app has no middleware currently, the underlying framework vulnerability means adding any middleware creates immediate security gaps.

### SEC-004 — HIGH: No Content Security Policy

No CSP header or meta tag is present. The rendered HTML includes multiple inline `<script>` blocks (`self.__next_f.push(...)`) that would fail under a strict CSP. Without CSP, XSS vulnerabilities in any future dynamic content have no mitigation layer. Fix: Implement CSP in `next.config.ts` `headers()` function.

### SEC-005 — MEDIUM: No X-Frame-Options (Clickjacking)

The application can be embedded in an `<iframe>` on any domain. Clickjacking attacks are possible if any sensitive actions are added. Fix: Add `X-Frame-Options: DENY` header.

### SEC-006 — MEDIUM: Missing HSTS Header

Without `Strict-Transport-Security`, browsers may make initial HTTP connections on first visit (before being redirected to HTTPS), enabling MITM attacks. Fix: Add HSTS header with `max-age=63072000; includeSubDomains; preload`.

### SEC-007 — LOW: Developer File Path Disclosure

The heading "To get started, edit the page.tsx file." discloses the internal file structure (`page.tsx`) to all users, confirming the use of Next.js App Router. This is minimal risk individually but aids attackers performing reconnaissance. Fix: Replace with production content.

### SEC-008 — LOW: README Discloses Framework and Scaffolding Origin

`README.md` in the repository root explicitly states the project was bootstrapped with `create-next-app` and links to the Next.js documentation. This should be updated or removed from public-facing deployments.

## 7. Performance Findings

### PERF-001 — First-Load JS: 517 KB Uncompressed

**Measured from:** `.next/diagnostics/route-bundle-stats.json`  
**Value:** 528,942 bytes (517 KB) uncompressed  
**Estimated gzipped:** ~175–200 KB  
**Impact:** Increases Time to Interactive (TTI) and Total Blocking Time (TBT)  
**Threshold:** Google recommends < 200 KB total JS for good TTI on mobile  
**Cause:** React 19 runtime + Next.js 16 client hydration + Turbopack runtime chunks — all loaded even for a purely static page  
**Recommendation:** Investigate disabling client-side hydration for fully static pages, or use `next export` for a zero-JS static site if no interactivity is needed.

### PERF-002 — Total First-Load Asset Budget

| Asset Type | Size (uncompressed) |
|---|---|
| JavaScript (7 chunks) | 517 KB |
| CSS (1 file) | 13.5 KB |
| Fonts (11 woff2 files) | 174 KB |
| SVG images (next.svg + vercel.svg) | ~6 KB |
| **Total** | **~710 KB** |

For a single-page app with static content and no API calls, 710 KB of assets is heavy. A well-optimized landing page should target under 200 KB total.

### PERF-003 — Font Loading: Two Google Fonts via Next.js Font

Both Geist and Geist Mono are loaded. Geist Mono is declared in `layout.tsx` but the `page.tsx` does not appear to use `font-mono` anywhere. This adds ~30–40 KB of woff2 for an unused font on this page.

**Recommendation:** Remove Geist Mono from the layout import if it is not needed for this page, or use font subsetting.

### PERF-004 — No `<link rel="preconnect">` for External Domains

Four external links point to `vercel.com` and `nextjs.org`. No DNS prefetch or preconnect hints are set. While these are anchor links (not API calls), adding preconnect would speed up navigation for users who click them.

**Recommendation:** Add to `layout.tsx` metadata or `<head>`:
```html
<link rel="preconnect" href="https://vercel.com">
<link rel="preconnect" href="https://nextjs.org">
```

### PERF-005 — Next.js Image Optimization: SVG Bypass

Next.js's `dangerouslyAllowSVG` is `false` in `images-manifest.json` (correct). However, both images (`/next.svg`, `/vercel.svg`) are served as raw SVG via `<img>` tags (not through `/_next/image`), bypassing the image optimization pipeline. SVGs are not processed by `sharp` and cannot be converted to webp. This is correct behavior, but means there is no lazy loading, size optimization, or webp serving for these assets.

### PERF-006 — No Bundle Analysis Tool Configured

`@next/bundle-analyzer` is not installed. Without it, it is impossible to visualize which packages contribute to the 517 KB JS bundle. This makes performance regression difficult to detect in CI.
