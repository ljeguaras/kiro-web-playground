### BUG-001 — Next.js Vulnerable to Denial of Service with Server Components
**Severity:** High | **Priority:** P1 | **Component:** Dependencies (next)

**Description:**  
The installed version of Next.js (16.2.4) is affected by a DoS vulnerability in Server Components. An unauthenticated remote attacker can craft a request that causes the server to consume excessive CPU/memory resources.

**Steps to Reproduce:**  
1. Deploy the app with `next start`
2. Send a crafted malicious request targeting Server Component rendering

**Expected Result:** Server handles requests normally  
**Actual Result:** Server can be forced into denial-of-service condition

**Advisory:** https://github.com/advisories/GHSA-8h8q-6873-q5fj  
**CVSS:** 7.5 (AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H)

**Suggested Fix:**  
```bash
npm install next@16.3.4
```
A non-breaking patch is available at version 16.3.4.

### BUG-002 — PostCSS XSS via Unescaped `</style>` Tag
**Severity:** High | **Priority:** P1 | **Component:** Dependencies (postcss)

**Description:**  
PostCSS ≤8.5.22 may output unescaped `</style>` sequences in CSS stringify, enabling XSS in scenarios where CSS output is injected into HTML pages. Affects the build toolchain and any SSR scenario.

**Advisory:** https://github.com/advisories/GHSA-qx2v-qp2m-jg93  
**CVSS:** 6.1 (AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N)

**Suggested Fix:** Upgrade to next@16.3.4 which pulls in a patched postcss version.

### BUG-007 — Missing Security Response Headers
**Severity:** Medium | **Priority:** P2 | **Component:** Security / HTTP Configuration

**Description:**  
No HTTP security headers are configured in `next.config.ts`. The following headers are missing from all responses:

| Header | Risk |
|--------|------|
| `Content-Security-Policy` | No XSS mitigation |
| `X-Frame-Options: DENY` | Clickjacking possible |
| `Strict-Transport-Security` | HTTPS not enforced |
| `X-Content-Type-Options: nosniff` | MIME sniffing attacks possible |
| `Permissions-Policy` | Browser feature restrictions absent |
| `Referrer-Policy` | Full URL sent in Referer header |

**Steps to Reproduce:**  
1. Deploy app, inspect response headers with DevTools Network tab
2. None of the above headers appear

**Suggested Fix:**  
Add to `next.config.ts`:
```ts
const nextConfig: NextConfig = {
  async headers() {
    return [{
      source: '/(.*)',
      headers: [
        { key: 'X-Frame-Options', value: 'DENY' },
        { key: 'X-Content-Type-Options', value: 'nosniff' },
        { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
        { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
      ],
    }];
  },
};
```
CSP and HSTS should be added once deployment environment is confirmed.

### BUG-008 — Duplicate `<title>` Tags on 404 Page
**Severity:** High | **Priority:** P1 | **Component:** UI / 404 Page

**Description:**  
The rendered `_not-found.html` page contains two `<title>` elements inside `<head>`:
1. `<title>404: This page could not be found.</title>`
2. `<title>Create Next App</title>`

This is invalid HTML (only one `<title>` permitted per `<head>`) and confuses screen readers, browser tab titles, and SEO crawlers.

**Steps to Reproduce:**  
1. Navigate to any non-existent path (e.g., `/does-not-exist`)
2. View page source, inspect `<head>` — two `<title>` tags are present

**Expected Result:** Single meaningful title: `404: This page could not be found.`  
**Actual Result:** Both titles exist; browser shows the last one which may be the generic app title

**Suggested Fix:**  
Create `app/not-found.tsx` to override the default 404 with proper metadata:
```tsx
import { Metadata } from 'next';
export const metadata: Metadata = { title: '404 – Page Not Found' };
export default function NotFound() { /* ... */ }
```

### BUG-009 — Non-Responsive Vertical Padding on Mobile
**Severity:** Medium | **Priority:** P2 | **Component:** UI / Responsive Design

**Description:**  
The `<main>` element uses `py-32` (8rem = 128px top + 128px bottom = 256px total vertical padding). On a typical mobile viewport (667px tall iPhone SE), this consumes ~38% of available height before any content renders.

**Steps to Reproduce:**  
1. Open app on iPhone SE (375×667) or Chrome DevTools at that size
2. Observe excessive top/bottom whitespace relative to content area

**Expected Result:** Comfortable but not excessive padding on mobile  
**Actual Result:** Content is squeezed into roughly 62% of the viewport

**Suggested Fix:**  
Replace `py-32` with `py-16 sm:py-32` (or similar responsive variant).

### BUG-010 — Non-Responsive Horizontal Padding on Narrow Viewports
**Severity:** Medium | **Priority:** P2 | **Component:** UI / Responsive Design

**Description:**  
`px-16` (4rem = 64px per side = 128px total) is applied at all viewport widths. On a 320px viewport (old iPhones, some Android devices), only 192px remains for actual content. The `max-w-xs` heading constraint is 20rem (320px), wider than the available content area, causing the heading to compete for space.

**Steps to Reproduce:**  
1. Chrome DevTools → 320×568 viewport
2. Observe cramped layout with excessive left/right whitespace

**Suggested Fix:**  
Use `px-6 sm:px-16` for a more comfortable mobile experience.

### BUG-012 — No Skip Navigation Link
**Severity:** High | **Priority:** P1 | **Component:** Accessibility

**Description:**  
The page has no skip-to-main-content link. Screen reader users and keyboard-only users must Tab through all focusable elements before reaching the main content. While the page only has a few focusable elements currently, this is a WCAG 2.1 AA requirement and will become critical as the application grows.

**WCAG Reference:** 2.4.1 Bypass Blocks (Level A)

**Suggested Fix:**  
Add to `layout.tsx` as the first element inside `<body>`:
```html
<a href="#main-content" class="sr-only focus:not-sr-only focus:absolute focus:top-4 focus:left-4">
  Skip to main content
</a>
```
And add `id="main-content"` to the `<main>` element.

### BUG-013 — External `_blank` Links Lack New-Tab Warning
**Severity:** High | **Priority:** P1 | **Component:** Accessibility

**Description:**  
All four links ("Templates", "Learning", "Deploy Now", "Documentation") open in a new tab (`target="_blank"`) with no indication to the user — visual or auditory — that a new tab will open. Screen readers will not announce this behavior. Sighted users have no visual icon.

**WCAG Reference:** 3.2.2 On Input, G201 Giving users advanced warning when opening a new window

**Suggested Fix:**  
Add visually-hidden text to each external link:
```tsx
<a href="..." target="_blank" rel="noopener noreferrer">
  Templates
  <span className="sr-only"> (opens in a new tab)</span>
</a>
```
Or add an SVG external-link icon visible to sighted users.

### BUG-014 — No `:focus-visible` Styles Defined
**Severity:** High | **Priority:** P1 | **Component:** Accessibility

**Description:**  
The Tailwind base reset includes `:-moz-focusring { outline: auto }` but no custom `:focus-visible` styles are defined anywhere in the codebase. Browser-default focus outlines vary significantly: some browsers (Chrome) show a blue outline, others render it poorly. Without explicit focus styles, keyboard navigation is unreliable.

**WCAG Reference:** 2.4.7 Focus Visible (Level AA), 2.4.11 Focus Appearance (Level AA)

**Suggested Fix:**  
Add to `globals.css`:
```css
:focus-visible {
  outline: 2px solid #0070f3;
  outline-offset: 2px;
  border-radius: 2px;
}
```

### BUG-015 — Missing Semantic HTML Landmark Elements
**Severity:** Medium | **Priority:** P2 | **Component:** Accessibility / Semantic HTML

**Description:**  
The application has a `<main>` element but is missing `<header>`, `<nav>`, and `<footer>` landmarks. This violates the workspace steering rule ("Semantic HTML for all layout sections") and WCAG 1.3.1 (Info and Relationships).

Screen reader users rely on landmark navigation (`<nav>` for navigation menus, `<header>` for page header, `<footer>` for footer information) to jump directly to sections.

**Current structure:**
```html
<body>
  <div> <!-- outer wrapper — no semantic element -->
    <main> <!-- present ✓ -->
      <!-- no <header> ✗ -->
      <!-- no <nav> ✗ -->
      <!-- no <footer> ✗ -->
    </main>
  </div>
</body>
```

**Suggested Fix:**  
Wrap the CTA links in a `<nav>` with `aria-label="External resources"`. Add `<header>` and `<footer>` as appropriate for the full application.

### BUG-017 — Documentation Button Border Fails WCAG 1.4.11 Contrast
**Severity:** Low | **Priority:** P3 | **Component:** Accessibility / Color Contrast

**Description:**  
The "Documentation" button uses `border-black/[.08]` (rgba(0,0,0,0.08)) on a white `bg-zinc-50` background. The computed border color is approximately `#ebebeb`, giving a contrast ratio of **1.19:1** against white — far below WCAG 1.4.11's 3:1 requirement for non-text UI components.

**Light mode border:** rgba(0,0,0,0.08) ≈ `#ebebeb` on `#fafafa` = **1.19:1** (FAIL, requires 3:1)

**Suggested Fix:**  
Increase border opacity to at least 30%: `border-black/30` gives approximately 2.4:1. For full compliance use `border-black/50` or higher. Alternatively, use a solid color: `border-zinc-300`.

### BUG-018 — Unused Geist Mono Font Loading
**Severity:** Medium | **Priority:** P2 | **Component:** Performance

**Description:**  
`layout.tsx` loads both `Geist` and `Geist Mono` font families. Geist Mono is only assigned to the `--font-geist-mono` CSS custom property. No element in the rendered page uses `font-mono` or any class that resolves to `--font-geist-mono`. The 11 Geist Mono WOFF2 files (~51KB+ combined) are loaded unnecessarily.

**Suggested Fix:**  
Remove the Geist Mono import from `layout.tsx` if not used:
```tsx
// Remove this:
import { Geist_Mono } from "next/font/google";
const geistMono = Geist_Mono({ ... });
// And remove geistMono.variable from html className
```

**Severity:** Low | **Priority:** P3 | **Component:** Performance

**Description:**  
The total JavaScript delivered for a fully static, zero-interactivity page is 626.5KB. This is almost entirely Next.js runtime overhead. While unavoidable with the current framework, it is worth flagging for a page that could be a plain HTML file.

**Breakdown:**

### BUG-020 — No `prefers-reduced-motion` Support
**Severity:** Medium | **Priority:** P2 | **Component:** Performance / Accessibility

**Description:**  
The CSS includes `transition-colors` animations on the CTA buttons (hover states). No `@media (prefers-reduced-motion: reduce)` rule exists to disable or minimize these transitions for users who have enabled the OS-level "Reduce Motion" accessibility setting.

**WCAG Reference:** 2.3.3 Animation from Interactions (Level AAA, recommended for AA compliance)

**Suggested Fix:**  
Add to `globals.css`:
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

### BUG-025 — Font Cascade Conflict in `globals.css`
**Severity:** Medium | **Priority:** P2 | **Component:** Code Quality

**Description:**  
`globals.css` contains:
```css
body {
  font-family: Arial, Helvetica, sans-serif;
}
```

This explicitly overrides the Tailwind CSS variable cascade at the `body` level. While the page content is wrapped in `font-sans` (which resolves to `var(--font-geist-sans)` correctly), any content rendered outside that wrapper — including the built-in Next.js 404 and 500 error pages' secondary content — will render in Arial instead of Geist.

**Suggested Fix:**  
Remove the `font-family` from the `body` rule in `globals.css`, or change it to:
```css
body {
  font-family: var(--font-geist-sans), Arial, Helvetica, sans-serif;
}
```

## 4. UX Improvement Suggestions

1. **Content placeholder replacement** — Replace all boilerplate text and links with meaningful application content. The heading "To get started, edit the page.tsx file." is entirely inappropriate for any real user.

2. **Mobile padding refinement** — Use responsive padding variants (`py-16 sm:py-32`, `px-6 sm:px-16`) for a more comfortable mobile experience.

3. **Button gap in the SM–MD range** — Add `sm:w-auto` to the CTA buttons to fix the awkward full-width buttons in a row at 640–767px.

4. **Visual new-tab indicator** — All external links open in new tabs. Add a small external-link icon (e.g., `↗`) beside each to set user expectations visually.

5. **Dark mode toggling** — The site only follows `prefers-color-scheme` media query with no manual toggle. Providing an explicit dark/light toggle improves user control.

6. **Loading state** — No loading indicators are defined. For future pages with data fetching, implement Suspense boundaries and skeleton loaders.

7. **Empty states** — No empty state UI exists. Define a design pattern for lists/tables with no data before building them.

8. **Error boundary** — The `_global-error` page uses inline styles inconsistent with the rest of the app. Create a custom `error.tsx` with branded styling.
