### BUG-002: Font Override Bug in globals.css

**Title:** Body `font-family: Arial` rule overrides Geist font CSS variable, making font loading redundant

**Severity:** Medium  
**Priority:** P2  
**Component:** app/globals.css  

**Description:**  
`layout.tsx` correctly loads the Geist font (via `next/font/google`) and injects `--font-geist-sans` and `--font-geist-mono` CSS variables into the `<html>` element. The `@theme` block in `globals.css` then maps these to `--font-sans` and `--font-mono`. However, an explicit `body { font-family: Arial, Helvetica, sans-serif; }` rule in `globals.css` overrides all of this on the `<body>` element, meaning Geist is never actually rendered.

**Playwright confirmation:** `window.getComputedStyle(document.body).fontFamily` returned `Arial, Helvetica, sans-serif` - confirming Geist is NOT being used.

**Steps to Reproduce:**
1. Open `http://localhost:3000` in a browser
2. Open DevTools > Computed styles on `<body>`
3. Observe `font-family: Arial, Helvetica, sans-serif`

**Expected Result:** Body should use Geist Sans (`var(--font-sans)` resolving to `--font-geist-sans`).

**Actual Result:** Body uses Arial (fallback font). Geist font files are loaded (~53KB) but never displayed. The Google Fonts API is called unnecessarily.

**Suggested Fix:**
Remove or replace the explicit `body` font-family rule in `globals.css`:
```css
/* REMOVE THIS: */
body {
  background: var(--background);
  color: var(--foreground);
  font-family: Arial, Helvetica, sans-serif; /* <-- DELETE THIS LINE */
}

/* The @theme block already maps --font-sans to Geist, so Tailwind's font-sans utility will work */
```

### BUG-003: Non-Semantic Outer Wrapper Element

**Title:** Outermost page container is `<div>` instead of a semantic HTML landmark

**Severity:** Medium  
**Priority:** P2  
**Component:** app/page.tsx  

**Description:**  
The root element returned by the `Home` component in `page.tsx` is a generic `<div>` with `className="flex flex-col flex-1 items-center justify-center bg-zinc-50..."`. This div wraps the `<main>` element and serves as the primary page layout container. Per accessibility best practices and the project's steering rules (requiring semantic HTML for all layout sections), this should be replaced with an appropriate semantic element.

**Playwright confirmation:** `document.body.firstElementChild.tagName` returned `"DIV"`. The accessibility snapshot shows the page rooted at `main` (Next.js strips the outer div from the a11y tree), but the DOM structure is non-semantic.

DOM structure observed:
```
<body>
  <div class="flex flex-col flex-1 ...">  <!-- BUG: non-semantic -->
    <main class="flex flex-1 w-full ...">
      ...
    </main>
  </div>
</body>
```

**Steps to Reproduce:**
1. Open `http://localhost:3000`
2. Inspect DOM with DevTools
3. Observe `<div>` as the first child of `<body>` wrapping `<main>`

**Expected Result:** Outermost layout container should be a semantic element such as `<div role="presentation">` if purely decorative, or refactored so `<main>` serves as the root (with background/layout styles applied directly to `<body>` or the `<html>` element, or via a CSS wrapper).

**Actual Result:** Generic `<div>` used as the full-page layout wrapper.

**Suggested Fix:**
Option A - Apply background to the body in CSS and remove outer div:
```tsx
// In globals.css, set bg-zinc-50 on body and remove the wrapping div
// Then in page.tsx:
export default function Home() {
  return (
    <main className="flex flex-1 w-full max-w-3xl flex-col items-center justify-between py-32 px-16 bg-white dark:bg-black sm:items-start mx-auto">
      {/* content */}
    </main>
  );
}
```
Option B - Use the outer div as an explicit landmark with a `role` attribute if it serves a structural purpose that doesn't map to a semantic element.

### BUG-004: Missing aria-label on CTA Links

**Title:** "Deploy Now" and "Documentation" CTA links lack aria-label, providing insufficient context to screen readers

**Severity:** Medium  
**Priority:** P2  
**Component:** app/page.tsx  

**Description:**  
Both call-to-action links at the bottom of the page ("Deploy Now" and "Documentation") open in new tabs (`target="_blank"`). Screen readers announce the link text directly, but without additional context, users may not understand:
- Where the link leads (it navigates to external Vercel/Next.js sites)
- That it opens in a new tab (which should be announced for accessibility)

The "Deploy Now" link compounds this by combining an image (`Vercel logomark`) and text within the same `<a>` element. The accessible name becomes "Vercel logomark Deploy Now" (confirmed by aria snapshot), which is verbose and awkward.

**Playwright aria snapshot:** `link "Vercel logomark Deploy Now"` - confirms the img alt text is prepended to the link accessible name.

**Steps to Reproduce:**
1. Navigate to `http://localhost:3000` with a screen reader enabled
2. Tab to the "Deploy Now" button
3. Listen to what the screen reader announces

**Expected Result:** Screen reader announces: "Deploy Now, opens in new tab" or similar with clear context.

**Actual Result:** Screen reader announces: "Vercel logomark Deploy Now" - redundant image alt text pollutes the link label.

**Suggested Fix:**
```tsx
<a
  aria-label="Deploy Now to Vercel (opens in new tab)"
  href="https://vercel.com/new?..."
  target="_blank"
  rel="noopener noreferrer"
  className="..."
>
  <Image
    aria-hidden="true"  {/* hide decorative logo from screen readers */}
    src="/vercel.svg"
    alt=""              {/* empty alt since aria-hidden */}
    width={16}
    height={16}
  />
  Deploy Now
</a>

<a
  aria-label="Read Next.js Documentation (opens in new tab)"
  href="https://nextjs.org/docs?..."
  target="_blank"
  rel="noopener noreferrer"
  className="..."
>
  Documentation
</a>
```

### BUG-005: No React Error Boundary

**Title:** No error boundary defined; unhandled component errors crash the entire application with a blank screen

**Severity:** Medium  
**Priority:** P2  
**Component:** app/layout.tsx / app/error.tsx (missing)  

**Description:**  
The application has no React error boundary at any level. If any component throws a JavaScript error during rendering, the entire app unmounts and displays a blank white screen (or Next.js's default error overlay in dev mode). In production, users would see a completely blank page with no recovery option.

Next.js App Router supports a special `error.tsx` file as a built-in error boundary - this file is absent.

**Steps to Reproduce:**
1. In `app/page.tsx`, temporarily add `throw new Error("Test error")` inside the component
2. Navigate to `http://localhost:3000` in production mode (`npm run build && npm start`)
3. Observe blank white screen with no user-friendly message

**Expected Result:** A user-friendly error message is displayed with options to retry or navigate back.

**Actual Result:** Entire application crashes with a blank screen or unhandled error overlay.

**Suggested Fix:**
Create `app/error.tsx`:
```tsx
'use client';

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <section className="flex flex-col items-center justify-center min-h-screen gap-4">
      <h2 className="text-2xl font-semibold">Something went wrong</h2>
      <p className="text-zinc-600">{error.message}</p>
      <button
        onClick={reset}
        className="rounded-full bg-foreground px-5 py-2 text-background"
      >
        Try again
      </button>
    </section>
  );
}
```

### BUG-006: No Content-Security-Policy Headers

**Title:** next.config.ts has no CSP headers configured, leaving the application vulnerable to XSS attacks

**Severity:** Medium  
**Priority:** P2  
**Component:** next.config.ts  

**Description:**  
No Content-Security-Policy (CSP) header is set anywhere in the application. Playwright security check confirmed `cspMetaPresent: false` and no CSP meta tag is present in the HTML. Without CSP, a successful XSS injection can:
- Execute arbitrary JavaScript in the user's browser
- Steal session data, cookies, or tokens
- Exfiltrate sensitive information

The app also loads resources from multiple external origins (vercel.com, nextjs.org, Google Fonts) with no whitelist.

Additionally, 9 inline `<script>` blocks were detected by Playwright (Next.js runtime bootstrapping), which a strict CSP would need to account for via nonces.

**Steps to Reproduce:**
1. Inspect HTTP response headers at `http://localhost:3000`
2. Observe absence of `Content-Security-Policy` header

**Expected Result:** A `Content-Security-Policy` header restricting script sources, style sources, and other resource types.

**Actual Result:** No CSP header present.

**Suggested Fix:**
Add security headers in `next.config.ts`:
```ts
const nextConfig: NextConfig = {
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          {
            key: 'Content-Security-Policy',
            value: [
              "default-src 'self'",
              "script-src 'self' 'unsafe-inline'",  // tighten with nonces for production
              "style-src 'self' 'unsafe-inline'",
              "img-src 'self' data:",
              "font-src 'self'",
              "connect-src 'self'",
              "frame-ancestors 'none'",
            ].join('; '),
          },
          { key: 'X-Frame-Options', value: 'DENY' },
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
        ],
      },
    ];
  },
};
```

### BUG-007: Focus Ring Relies on Browser Default (No Explicit Tailwind Focus Styles)

**Title:** Interactive links have no explicit focus:ring Tailwind utilities; visual focus indicators depend on browser defaults

**Severity:** Medium  
**Priority:** P2  
**Component:** app/page.tsx  

**Description:**  
None of the four interactive links on the page have explicit `focus:` Tailwind utility classes. The focus ring is provided entirely by browser default styles.

**Playwright measurement:**
- Focus ring on "Documentation" (last tabbed element): `outline: rgb(23, 23, 23) auto 1px`
- `outlineWidth: "1px"` - this is thin and relies on the browser's UA stylesheet
- The `auto` outline style is an OS-level focus ring (acceptable on some platforms, invisible on others)

On browsers/OS combinations that render a very thin or invisible default outline (e.g., Chrome on macOS renders a thin blue outline; some browsers have removed default outlines entirely), keyboard users cannot see where focus is.

The CTA links (rounded-full pill buttons) have `transition-colors` but no `focus-visible:ring-*` utilities.

**Steps to Reproduce:**
1. Navigate to `http://localhost:3000`
2. Press Tab key repeatedly to cycle through all 4 links
3. Observe the focus ring on each element (especially on macOS Chrome)

**Expected Result:** All interactive elements show a clearly visible, high-contrast focus ring that meets WCAG 2.4.7 (minimum 3:1 contrast against adjacent colors).

**Actual Result:** Focus ring relies on browser default (`outline: auto 1px`) which may be invisible or insufficient on some platforms.

**Suggested Fix:**
Add explicit focus-visible styles to all interactive elements:
```tsx
// For inline text links
className="font-medium text-zinc-950 dark:text-zinc-50 focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-offset-2 focus-visible:ring-zinc-950"

// For CTA pill buttons
className="... focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-offset-2 focus-visible:ring-zinc-950"
```

### BUG-010: Next.js Logo Image Aspect Ratio Mismatch

**Title:** Next.js logo declared as 100x20 pixels but SVG natural dimensions are 300x61, causing potential rendering distortion

**Severity:** Low  
**Priority:** P3  
**Component:** app/page.tsx  

**Description:**  
The `<Image>` component for the Next.js logo uses `width={100} height={20}`. The SVG file (`/next.svg`) has natural dimensions of 300x61 pixels (confirmed via Playwright). The declared aspect ratio (100/20 = 5.0) differs from the natural aspect ratio (300/61 = 4.92), which causes the Next.js Image component to emit a browser console warning about aspect ratio modification.

**Playwright confirmation:**
- Browser console warning: `Image with src "http://localhost:3000/vercel.svg" has either width or height modified, but not the other`
- Natural dimensions: `naturalWidth: 300, naturalHeight: 61` but declared as `100 x 20`
- Rendered: `cssHeight: "20.2969px"` (slight discrepancy from integer 20)

Note: A similar warning was generated for the Vercel SVG logo (naturalWidth: 173, naturalHeight: 150; rendered as 16x14 due to CSS).

**Steps to Reproduce:**
1. Open browser DevTools console at `http://localhost:3000`
2. Observe warning about image aspect ratio

**Expected Result:** No console warnings; image dimensions match natural aspect ratio.

**Actual Result:** Console warning emitted; image may render slightly distorted.

**Suggested Fix:**
```tsx
<Image
  className="dark:invert"
  src="/next.svg"
  alt="Next.js logo"
  width={100}
  height={21}  // correct: 100 * (61/300) = 20.33, round to 21
  priority
/>
```
Or use `height="auto"` with CSS to preserve natural aspect ratio:
```tsx
<Image
  className="dark:invert h-auto"
  src="/next.svg"
  alt="Next.js logo"
  width={100}
  height={21}
  priority
/>
```

## 4. UX Improvement Suggestions

### UX-001: Add Loading State / Skeleton Screen
The page renders completely on the server (SSR), but in production scenarios with slow connections, adding a loading skeleton would improve perceived performance for any async content.

### UX-002: Improve CTA Button Hover Animations
The CTA buttons have `transition-colors` but transitions are instantaneous. Adding a duration (`transition-colors duration-200`) provides a smoother, more polished feel.

### UX-003: Add `rel="noopener noreferrer"` to Inline Links
The "Templates" and "Learning" inline links have `target=""` (opens in same tab) but carry no `rel` attribute. If they were changed to open in new tabs, adding `rel="noopener noreferrer"` would be necessary for security. Currently they open in the same tab - consider if that's intentional, as it would navigate users away from the page.

### UX-004: Responsive Typography
At 375px (mobile), the H1 heading (`max-w-xs text-3xl`) may feel large relative to the container. Consider reducing to `text-2xl` on mobile via responsive modifiers for better readability.

### UX-005: Dark Mode - Redundant Background Colors
In dark mode, both the outer `<div>` (`dark:bg-black`) and the `<main>` element (`dark:bg-black`) use identical background colors. The outer wrapper's dark mode class is redundant and adds unnecessary CSS. Remove `dark:bg-black` from the outer div or consolidate background management.

### UX-006: Consider Adding a Skip Navigation Link
For keyboard users, a "Skip to main content" link at the top of the page allows bypassing any repeated navigation before reaching the main content area. While this page has no top navigation, establishing this pattern now is best practice.

### UX-007: External Links Should Warn Users (WCAG 3.2.5)
The two CTA links open in new tabs (`target="_blank"`) without informing users. A visual indicator (external link icon) or `aria-label` mentioning "opens in new tab" should be added. Currently only `rel="noopener noreferrer"` is present.
