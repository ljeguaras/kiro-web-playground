# QA audit deliverable review (v1) - QA_AUDIT_REPORT.md

The deliverable is a single Markdown document, `QA_AUDIT_REPORT.md`, produced for a comprehensive manual QA audit of a minimal Next.js 16.2.4 create-next-app starter that has exactly one real route. The report is grounded in six evidence files and four screenshots captured during FEAT-001, and it marks the many non-existent feature categories (forms, auth, tables, CRUD, etc.) as Not Applicable rather than fabricating findings. This review cross-checks every substantive claim against the evidence, verifies the nine required deliverables and their exact formatting constraints, and checks the internal consistency of the counts and verdict.

Watch for: one reconciliation gap (10 bugs vs. 9 "failed" checks) explained in prose but not made airtight; one explicitly-requested verification item (the "Learning" link text vs. "the Learning center" copy) dropped from the report; a score whose stated deductions do not sum to 82.

**Verdict**: NEEDS_CHANGES

## Deliverable completeness and format constraints

All nine required deliverables are present, in order, under numbered headings: QA Summary, Bug Report Table, Detailed Bug Reports, UX Improvement Suggestions, Security Findings, Accessibility Findings, Performance Findings, Production Readiness Score, Final Recommendation. The bug-table header is exactly `| ID | Severity | Priority | Component | Description |`. The Final Recommendation is exactly "Ready with Minor Fixes", one of the four allowed phrases. Each detailed bug carries Title, Description, Steps to reproduce, Expected result, Actual result, Suggested fix, and a Screenshot reference (or N/A). The em-dash constraint holds: a scan finds zero `—` characters. These are hard acceptance criteria and they all pass.

## Faithfulness to the evidence

Every checkable claim traces to an evidence file, with no fabrication and nothing that the evidence contradicts:

- Arial-vs-Geist body override (BUG-001): `app/globals.css` ends with `body { ... font-family: Arial, Helvetica, sans-serif; }`; evidence-ui.txt section 1 records `document.body` computing Arial while the `.font-sans` subtree computes Geist. The report's nuance that visible content still renders Geist because it sits inside `<div class="font-sans">` matches source and evidence.
- Inline-link target/rel asymmetry (BUG-002): source and evidence-ui.txt section 2 confirm the two inline anchors lack `target`/`rel` while the two button anchors carry `target="_blank" rel="noopener noreferrer"`; no active tabnabbing risk today because the inline links open in the same tab.
- Placeholder metadata (BUG-003): evidence-ui.txt section 5 records `<title>Create Next App</title>` and description "Generated by create next app".
- next/image aspect-ratio warning (BUG-004): evidence-console.txt captures the verbatim WARNING for `vercel.svg`; source confirms `<Image width={16} height={16}>` inside a flex button.
- Inline links no underline (BUG-005): evidence-a11y.txt section 6 records `text-decoration-line: none`, weight 500, near-black color.
- Landmarks (BUG-006): evidence-a11y.txt section 5 records main:1, header:0, footer:0, nav:0.
- Focus indicator UA-default only (BUG-007): evidence-a11y.txt section 2.
- Outline button low-contrast border (BUG-008): source shows `border-black/[.08]`; evidence-a11y.txt describes ~8% alpha black border.
- No manual dark-mode toggle (BUG-009): evidence-ui.txt section 4, correctly framed as a UX limitation.
- Dependency vulns (BUG-010): evidence-build.txt records "7 vulnerabilities (1 low, 6 high)", the same transitive chains plus the next@16.2.4 advisory range, and the note that none are exploitable in this feature set.
- Lint clean (exit 0), build clean (exit 0), no 5xx/CORS/auth failures, contrast passing, static prerender, ~16.8 KB HTML: all match the lint/build/network/a11y evidence.

The report quarantines dev-only noise (HMR WebSocket `ERR_CONNECTION_REFUSED`, React DevTools info) as non-production and declines to quote a first-load-JS figure because Next 16.2.4's Turbopack route table does not emit it (evidence-build.txt). Both are non-obvious calls the evidence supports, and getting them right avoids two common false findings.

## Not-Applicable handling

The Testing Scope table enumerates every user-requested category and marks the absent ones Not Applicable with a reason, rather than inventing findings for forms, auth, CRUD, etc. This satisfies the acceptance criterion that non-existent categories be explicitly documented.

## Count reconciliation and score traceability

The pass/fail arithmetic is internally consistent: the summary enumerates 30 checks yielding 21 pass + 9 fail. The soft spot is the relationship between "9 failed checks" and "10 bugs": BUG-010 is sourced from the `npm install` step, itself listed as check #1 PASS, so it is an orphan relative to the 30-check tally. Separately, the deduction list justifying the 82 score sums to -15 (would give 85). Neither is fabrication, but both undercut reproducibility. See Issues 1 and 3.

## Severity, priority, and verdict calibration

The severity/priority spread (5 Medium/P2, 5 Low/P3, no Critical/High) is defensible: nothing is a functional breakage, the Medium items are legitimate pre-production polish/hygiene concerns, and the Low items are robustness nits. "Ready with Minor Fixes" is consistent with clean lint/build, correct rendering, no auth/data surface, and no Critical/High defects. Only the numeric derivation of 82 needs correction.
