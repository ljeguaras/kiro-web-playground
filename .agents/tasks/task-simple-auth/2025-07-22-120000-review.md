# Simple auth system with JSON file storage and JWT sessions

This change adds a complete signup/login/logout flow to a Next.js 16 app. Users authenticate with username and password (no email), passwords are hashed with bcryptjs, sessions are stateless JWTs (jose, HS256) stored in httpOnly cookies, and route protection happens in proxy.ts (the Next.js 16 replacement for middleware.ts). The JSON file store at `data/users.json` is an intentional simplification for a demo app.

**Watch for:** The `updateSession` function extends the cookie expiry without re-signing the JWT, so the JWT's internal `exp` claim becomes stale and will eventually cause the proxy to reject a session the cookie still considers valid (confirmed). The proxy protects routes by exact path match, so any future sub-path like `/dashboard/settings` bypasses protection entirely (confirmed). Race condition in the JSON file store can silently lose user registrations under concurrent signups (confirmed).

## High-level view

The auth flow follows the Next.js 16 docs pattern closely: Server Actions validate with Zod, hash and compare passwords, then create or destroy a session cookie. The proxy.ts file correctly exports `proxy` (not `middleware`) and duplicates the JWT decrypt logic inline to avoid importing `server-only` code — a pragmatic trade-off documented in the task findings.

Session lifecycle has a subtle inconsistency: `createSession` signs a JWT with a 7-day `exp` claim and sets a 7-day cookie expiry, but `updateSession` only refreshes the cookie expiry without re-signing the JWT payload. After the original 7 days, the JWT's `exp` will fail verification even though the cookie is still being served.

The proxy protects routes by exact path match (`["/dashboard"]`), so any sub-path like `/dashboard/settings` would bypass the check entirely. This matters the moment the app grows beyond a single protected page.

The JSON file database is a read-all/write-all approach with no concurrency control. Two simultaneous `createUser` calls will both read, both append, and one write will overwrite the other. For a demo this is tolerable, but the failure mode is silent data loss, not an error.

1. **updateSession doesn't re-sign the JWT** (confirmed) — the cookie expiry is extended but the JWT's internal `exp` claim remains unchanged, causing a mismatch that will reject sessions after the original 7-day window. Re-encrypt a fresh JWT with a new `exp`.

3. **Race condition in JSON file store** (confirmed) — concurrent signups can lose data because `createUser` does a non-atomic read-modify-write. Use file locking or switch to an append-only strategy.
4. **SESSION_SECRET has no startup guard** (confirmed) — if `process.env.SESSION_SECRET` is undefined, `TextEncoder.encode(undefined)` produces an empty Uint8Array that jose rejects at signing time. The app won't silently misbehave, but it will crash with an opaque jose error on the first auth attempt rather than failing clearly at startup. Add an assertion that checks for the secret at module load.
5. **Home page redirect for authenticated users** (confirmed) — the proxy redirects authenticated users away from `/`, `/login`, and `/signup` to `/dashboard`, meaning a logged-in user can never visit the home page. May be intentional for a demo but worth a conscious decision.

## Session lifecycle mismatch

`updateSession` re-reads the existing cookie, verifies it, then calls `cookieStore.set` with a new `expires` date pushed 7 days into the future, but it re-uses the *original* signed JWT string:

```typescript
cookieStore.set("session", session, {   // same old JWT
  expires: expires,                       // new cookie expiry
});
```

The JWT's `exp` claim still says the token expires at its original creation time + 7 days. Once that internal expiry passes, `jwtVerify` in both proxy.ts and session.ts will reject the token even though the browser is still sending it (the cookie hasn't expired). The fix is to decrypt, rebuild a fresh payload with a new `expiresAt`, re-sign, and set the new JWT as the cookie value.

## Proxy route matching is exact-path only

```typescript
const protectedRoutes = ["/dashboard"];
const isProtectedRoute = protectedRoutes.includes(path);
```

This means `/dashboard` is protected but `/dashboard/settings`, `/dashboard/admin`, or any nested route is not. A `startsWith` check or a path-prefix approach would close this gap before sub-pages are added. The DAL's `verifySession` provides a second layer of defense at the Server Component level, but only if every new protected page remembers to call it — the proxy should be the authoritative gate.

## JSON file store race condition

`createUser` performs read → append → write as three separate async operations with no file lock:

```typescript
const users = await readUsers();
users.push(newUser);
await writeUsers(users);
```

If two requests hit signup concurrently, both read the same array, both append their user, and the second write silently overwrites the first. The failure mode is silent data loss — no error, no duplicate detection.

## Secret key initialization

Both `proxy.ts` and `app/lib/session.ts` execute `new TextEncoder().encode(process.env.SESSION_SECRET)` at module top-level. If the env var is missing, this produces a zero-length key that jose rejects with `"Data provided to an operation does not meet requirements"` on the first sign/verify call. The error is opaque and appears at request time rather than at startup. A guard like `if (!process.env.SESSION_SECRET) throw new Error("SESSION_SECRET is required")` at module top-level would surface the misconfiguration immediately.
